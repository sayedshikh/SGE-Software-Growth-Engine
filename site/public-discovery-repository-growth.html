Commercial-source safety gate

  • Keep paid application source, private configuration, secrets, customer data, keys, database dumps and release credentials out of public showcase repositories.
  • Review dependencies, third-party notices, licenses, bundled assets and redistribution rights before any source release.
  • A README, screenshots, demo, public docs, feature overview and selected changelog can showcase a product without publishing the commercial source.
  • Do not add an open-source license unless the repository contents and intended reuse rights have been reviewed. A license does not prevent copying when it grants reuse.
  • Public releases should contain only explicitly approved artifacts; verify hashes and package contents before release.

Channel playbooks & gates

SHOWCASE

GitHub

Publish a useful public-facing repository containing approved documentation, screenshots, demo, support route and a clear commercial-source boundary. Topics should accurately describe the project. Consider free public-repository security features, including secret scanning and alerts where available.

Gate: content, license scope, secrets and assets reviewed.

COMMUNITY

Reddit

Participate through helpful answers and genuine technical context. Check the current rules and moderation expectations of each community before posting. Do not use repetitive promotional posts, automated messaging or fabricated endorsements.

Gate: rules reviewed; post provides community value; promotional restrictions satisfied.

DEMO

Show HN

Reserve for a genuinely usable demo or product with a compelling maker story and the ability to engage with questions. Prepare the maker comment and be available after launch.

Gate: working demo, accurate description, maker availability and submission-rule review.

OPEN SOURCE ONLY

awesome-selfhosted

Conditional opportunity only. The project must meet the list's current inclusion rules and open-source licensing requirements. Do not expose paid source simply to qualify. Consider a separately maintained genuinely open component only if it has independent value and a suitable license.

Gate: verify current repository policy and license compatibility before considering submission.

LISTINGS

AlternativeTo & SaaSHub

Prepare accurate descriptions, categories, alternatives, screenshots, links and verification materials. Verify eligibility, fees and current submission rules independently. Do not assume approval or ranking.

Gate: product released, claims verified, current rules checked.

TECHNICAL CONTENT

Dev.to & Hashnode

Write real build notes, technical lessons, architecture tradeoffs, installation guides and troubleshooting posts. Avoid misleading claims or thin promotional articles.

Gate: article provides useful standalone information and links contextually.

LAUNCH

Product Hunt

Defer until release readiness, support, media, demo, positioning and launch engagement are prepared. Verify current platform rules and launch requirements.

Gate: launch checklist, product readiness and support plan reviewed.

FEEDBACK

Indie Hackers & technical communities

Share real progress, honest lessons and questions. Use actual product state and outcome data; never fabricate traction, sales or customer evidence.

Gate: contribution and community fit checked.

Suggested README structure

  1. One-sentence positioning and audience.
  2. Real screenshots or short demo.
  3. Problem solved and verified feature summary.
  4. Who it is and is not for.
  5. Requirements, install/demo instructions and limitations.
  6. Support, feedback and security-reporting route.
  7. Commercial offer, license boundary and purchase link.
  8. Changelog and verification notes.

Repository security checklist

  • Use secret scanning and push protection where available; check settings and limitations.
  • Consider Dependabot alerts and code scanning for suitable repositories.
  • Include a responsible security contact or SECURITY.md when appropriate.
  • Review every release archive and commit history for secrets before publishing; deleting a file later does not necessarily remove exposure from history.
  • Use minimal, deliberate repository permissions and protect important branches where appropriate.
